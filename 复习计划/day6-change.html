错误做法

错在哪里
缺少三道关键判断：
✗ 未形成正式变更请求
✗ 未分析影响
✗ 未经过审批

看起来省了一步，后面往往要补更多步骤。

02标准变更路径

阶段一：先判断
提出并记录 → 分析影响
  • 评估范围、进度、成本、质量、资源、风险、采购、合同
  • 不是只看“能不能做”，而是看“做了以后整个项目会变成什么样”
阶段二：再决策
审批
  • 结果：批准 / 拒绝 / 推迟
CCB
Change Control Board · 变更控制委员会

作用：审查、批准、拒绝或推迟变更。并非所有变更都固定由 CCB 审批，具体看授权机制。

阶段三：批准以后
更新 → 执行 → 监控
  • 更新项目管理计划
  • 更新范围 / 进度 / 成本等相关基准
  • 指导与管理项目工作 → 实施批准的变更
  • 继续监控结果
审批 ≠ 实施
实施整体变更控制

决定做不做。先审批，再执行。

指导与管理项目工作

批准以后真正去做。

03四类变更请求

判断关键：事情有没有已经发生？

纠正措施
Corrective Action

偏差已经发生，把绩效拉回计划。

进度落后 → 增加资源追回
预防措施
Preventive Action

偏差还没发生，提前防患于未然。

预计缺人 → 提前准备人员
缺陷补救
Defect Repair

产品已经有缺陷，修复它。

测试发现 Bug → 修复
更新
Update

修改正式受控内容，批准后改计划、基准或文件。

需求变更后更新范围基准

04你能判断吗？

四道判断题
客户提出变更 = 必须接受？✗
批准变更 = 已经实施？✗
变更发生后再补手续？✗
先分析影响，再审批？✓
变更控制不是限制变化，而是防止项目在变化中失去基准。
