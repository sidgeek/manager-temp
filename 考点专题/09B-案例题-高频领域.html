①进度管理 · 9 次 / 175 分（每次必考）

计算 + 找错双高频。计算部分详见 ② 关键路径 CPM、③ 三点估算、④ 进度压缩。

计算必背公式

六时标（先正推、后逆推） 正推：ES(首活动) = 0 EF = ES + 工期 多紧前活动 → ES = MAX(所有紧前 EF) 逆推：LF(末活动) = 总工期 LS = LF − 工期 多紧后活动 → LF = MIN(所有紧后 LS) 总浮动 TF = LS − ES = LF − EF TF = 0（或最小）→ 关键活动 自由浮动 FF = MIN(紧后活动 ES) − 本活动 EF 三点估算 PERT 期望工期 Te = (To + 4×Tm + Tp) / 6 标准差 σ = (Tp − To) / 6 项目总工期 T = Σ Te 项目总标准差 = √(Σ σ²) 概率：±1σ = 68.26% ±2σ = 95.46% ±3σ = 99.73% 进度压缩 赶工 = 加资源 → 加成本 快速跟进 = 并行 → 加风险 资源优化 资源平衡 = 改关键路径（工期变长） 资源平滑 = 不改关键路径

「进度方面存在的问题」找错清单

  1. 未制定进度管理计划／无进度基准，无法衡量偏差
  2. 活动定义不完整遗漏活动（常见：漏测试、漏上线、漏培训、漏数据迁移）
  3. 活动排序错误依赖关系（FS/SS/FF/SF）没理清，漏掉强制性依赖
  4. 工期估算不准凭经验拍脑袋，未用三点估算、未参考历史数据、未做专家判断
  5. 未识别关键路径精力平均分配，没盯住关键活动
  6. 关键路径上资源不足却去优化非关键路径的活动
  7. 进度压缩方法选择不当盲目赶工不看成本斜率；盲目并行不看返工风险
  8. 未做资源平衡/资源平滑人员严重过载、同一人同时被多个活动占满
  9. 进度监控缺失没有定期检查点，问题暴露太晚
  10. 出现延期后未及时纠偏未采取纠正措施或纠正措施无效

②质量管理 · 9 次 / 164 分（最好套模板）

三过程 + QA/QC 辨析（填空常考）

管理质量 QA（质量保证）控制质量 QC（质量控制）
关注过程、体系、过程改进可交付成果、是否达标
时机全过程（事前 / 事中）事后检查、验收前
手段质量审计、过程分析检查、测试、统计抽样、核查表
输出变更请求、质量报告核实的可交付成果、质量控制测量结果
口诀「QA 管过程防未病，QC 管结果查已病」

七种基本质量工具（年年考填空）

  • 因果图（鱼骨图 / 石川图）—— 找根本原因
  • 流程图 —— 展示过程步骤与可能出问题的环节
  • 核查表（计数表）—— 收集数据、统计缺陷频次
  • 帕累托图 —— 按频次排序 + 累计百分比，80/20 法则找"少数关键原因"
  • 直方图 —— 特殊形式条形图，描述集中趋势、分散程度、分布形状
  • 控制图 —— 判断过程是否受控（上下控制界限、连续 7 点在均值同侧判异常）
  • 散点图 —— 看两个变量之间的相关性

质量成本（判断分类常考）

一致性成本（主动投入）
  • 预防成本：培训、评审、过程改进、质量规划
  • 评估成本：测试、检查、破坏性测试、计量设备
非一致性成本（被动损失）
  • 内部失败：返工、废品、停工（交付前发现）
  • 外部失败：保修、退货、投诉、诉讼（交付后发现）

「质量管理方面存在的问题」找错清单

  1. 未制定质量管理计划或计划未经评审、未明确质量测量指标与验收标准
  2. QA 与 QC 职责混淆把"检查"当成"保证"，只做测试不做过程改进
  3. QA 缺乏独立性由开发人员兼任、或向项目经理汇报（QA 应保持独立，向高层/PMO 汇报）
  4. 未做质量审计无法验证质量过程的合规性
  5. 未做技术评审 / 设计评审或评审会由被评审者本人组织（应独立组织）
  6. 质量测量指标不明确需求不可度量，验收无标准
  7. 重检验轻预防一致性成本投入不足，只在末期"救火"
  8. 质量责任不清无责任分配矩阵，出了问题互相推诿
  9. 发现缺陷未做根本原因分析只改表面现象，同类问题反复出现
  10. 缺陷修复后未回归验证变更/返工后未确认是否真正解决

③整合管理 · 7 次 / 130 分（变更 · 配置 · 收尾）

整合管理的案例题就这三个壳，其中配置管理近三年明显升温（2023.05、2022.05 广东、2016.11 均考）。

A · 变更管理

八步流程 · 填空题原句
  • ① 提出与接受变更申请
  • ② 对变更的初审
  • ③ 变更方案论证
  • ④ CCB（变更控制委员会）审查批准
  • ⑤ 发出变更通知并实施
  • ⑥ 变更实施的监控
  • ⑦ 变更效果评估
  • ⑧ 判断变更后项目是否已纳入正常轨道
找错清单
  1. 无变更控制流程或流程不规范、未定义 CCB 职责
  2. 变更未书面化口头、电话、即时消息一句话就改了，无变更请求单
  3. 变更未经 CCB 审批就实施项目经理或开发人员擅自修改 （最常见）
  4. 未做变更影响分析没评估对范围/进度/成本/质量/风险/合同的影响
  5. 变更未通知干系人客户、团队、供应商不知情
  6. 变更后未更新计划与基准文档、进度基准、成本基准未同步
  7. 无变更日志变更无记录，无法追溯、无法统计
  8. 变更后未验证确认改完就走，没确认是否达到预期
  9. 变更频繁的根因未解决追溯到：需求未确认、范围不明确、合同条款含糊

B · 配置管理（近几年超高频）

6 项活动
制定配置管理计划 → 配置项标识 → 配置项控制 → 配置状态报告 → 配置审计 → 发布管理与交付
三库对照（判断题常考）
库别名存放内容权限
开发库动态库 / 工作库开发中、未评审的半成品开发者自己可改
受控库主库已评审通过、成为基线的配置项严格受控，须审批
产品库静态库 / 发行库已定型、可交付的产品只读
版本号规则
  • 草稿：0.x（如 0.68 —— 处于草稿状态）
  • 正式：x.y（如 V2.1 —— y 为小版本号，一般 y ∈ 0–9）
  • 修改：x.yz（如 V2.13 —— 正在修改中）
  • 配置审计两种：功能配置审计（符合功能需求吗）+ 物理配置审计（东西齐不齐、一致吗）
找错清单
  1. 未制定配置管理计划
  2. 未识别配置项／未给配置项编号、未定义命名规则
  3. 三库未建或混用开发库与受控库不分、直接改主库
  4. 未建立基线无需求基线 / 设计基线 / 产品基线
  5. 版本管理混乱文档版本与实物不一致、历史版本未保留
  6. 权限管理失控人人都可读写受控库
  7. 变更不走配置控制流程改了不申请、不记录、不评审
  8. 未做配置审计功能审计 + 物理审计都缺
  9. 无专职配置管理员或由开发人员兼职
  10. 未做配置状态报告配置项当前状态无人知晓

C · 项目收尾（2017.11 考过）

  • 收尾两类：合同收尾（结清合同、完成验收）+ 行政收尾（管理收尾）
  • 行政收尾核心：确认可交付成果已交付验收 → 项目档案归档 → 经验教训总结 → 释放资源 → 最终产品移交
  • 项目总结会：应在项目正式结束前召开；参加者含全体成员与主要干系人；讨论技术绩效、管理绩效、人员绩效、经验教训、遗留问题
